# Contexto del proyecto — Sistema de Autenticación Centralizado SSO / Conecta MINEDEC (SSO C2.2)

Manual de contexto MINEDEC para agentes de IA y desarrolladores.

> **Nota:** Spec Kit (extensión `agent-context`) gestiona el `AGENTS.md` e inyecta una **sección gestionada** (referencias al plan activo y tecnologías) delimitada por los marcadores `SPECKIT START` / `SPECKIT END`. Este manual es el **contenido estático MINEDEC** que convive con esa sección gestionada: no borres esa sección.

Personas y agentes de IA están sujetos a `.specify/memory/constitution.md` (Constitución MINEDEC 2.11.0). Este manual resume el stack **ya ratificado**, la **arquitectura multirrepositorio en GitLab (`git.sitimapa.co`)**, el alcance del **Subcomponente C2.2** y el flujo diario.

## Alcance y Arquitectura Multirrepositorio en GitLab (Solo Subcomponente C2.2)

El desarrollo del **Subcomponente C2.2 (Sistema de Autenticación Centralizado SSO / Conecta MINEDEC)** se estructura en **repositorios independientes dentro de GitLab (`git.sitimapa.co`)** (Principios IV y XVIII):
1. **Repositorio de Gobernanza y Especificaciones (`minedec-sso`, este repositorio)**: Contiene la Constitución (`.specify/memory/constitution.md`), la base de conocimiento OKF (`knowledge/`), los artefactos Spec Kit (`specs/00X-slug/`), esquemas DBML (`docs/esquemas-bd/*.dbml`) y contratos OpenAPI transversales. **No contiene archivos `.tf` estáticos de infraestructura base de GCP**.
2. **Repositorios Independientes de Paquete y Microservicios (`c2-sso/microservicios/*`, mapeados localmente en `../microservicios/<servicio>`)**: Cada paquete y servicio reside en su propio repositorio Git (`shared`, `pip-identity-service`, `sincronizador`, `conciliacion-job`, `sso-oidc`, `motor-pdp`, `api-pap`, `frontend`, `publicador-job`) con su propio `package.json`, `Dockerfile` y pipeline `.gitlab-ci.yml` (que compila, ejecuta SAST/SCA y pruebas con cobertura `>= 70%`, y publica imágenes en Artifact Registry `sso-containers` con `$CI_COMMIT_SHA`). El paquete transversal `@minedec/shared` (`../microservicios/shared`) se versiona y publica en el **GitLab NPM Package Registry** (`https://git.sitimapa.co/api/v4/projects/<PROJECT_ID>/packages/npm/`) para ser consumido como dependencia versionada por cada microservicio.
3. **Repositorio Central de Infraestructura (`c2-sso/devops/iac-terraform`, mapeado localmente en `../iac-terraform`)**: Repositorio independiente dedicado únicamente a Terraform HCL (`1.5.7`, sin Terragrunt), estructurado en **3 capas** (`modulos/`, `plantillas/` y `despliegues/<ambiente>/{devops,data,apps}` para `des`, `pre`, `pro`), empaquetado mediante `scripts/bundle.sh` (`--local-source="."` con `--tf-version-constraint="1.5.7"`) y con estado remoto administrado de forma 100% nativa por **Google Cloud Infrastructure Manager** (`config.googleapis.com` vía `sa-infra-manager@<project_id>.iam.gserviceaccount.com`). No incluye el stack `host` porque la **Red Compartida (Shared VPC)** es administrada por el equipo de redes en los proyectos host `mec-003-sha-net-des` (Desarrollo), `mec-003-sha-net-pre` (Preproducción) y `mec-003-sha-net-pro-511014` (Producción), sobre los cuales operan los proyectos de servicio SSO `mec-003-sso-des`, `mec-003-sso-pre` y `mec-003-sso-pro`.
4. **Sincronización de Ramas (`spec/00X-slug`)**: Cada feature utiliza una rama `spec/00X-slug` en espejo con `specs/00X-slug/` (`.specify/feature.json`). Cuando una feature requiere cambios tanto en código como en infraestructura GCP, se mantiene la misma rama `spec/00X-slug` sincronizada en los repositorios involucrados.

Componentes del Subcomponente C2.2 (5 servicios en GKE Autopilot: `sso-oidc`, `motor-pdp`, `api-pap`, `frontend`, `pip-identity-service` + Cloud Run):
- **Servicio Intermediario OIDC (`sso-oidc`, `DA-11`)**: *Identity Broker* en GKE Autopilot (`Node.js 22 + Express 5 + oidc-provider` certificado por la OpenID Foundation, `../microservicios/sso-oidc`) publicado detrás del External Application Load Balancer + Cloud Armor (`https://login.sso.<dominio>`, sin IAP delante) con los endpoints `GET /.well-known/openid-configuration`, `GET /authorize`, `GET /callback`, `POST /token`, `GET /jwks` y `GET/POST /logout`. Tiene al SSO como único cliente OAuth 2.0 registrado en Google Cloud Identity (`D-01`), mantiene la sesión central y códigos efímeros en Memorystore for Redis y emite a cada aplicación (Patrón 1 y PEP del Patrón 2) un `id_token` firmado con `RS256` (llaves en Secret Manager) con `aud` exclusivo por aplicación a partir de `client_id` y `redirect_uris` registrados en AlloyDB.
- **Motor de Autorización Central (`motor-pdp`) y Directorio PIP (`pip-identity-service`)**: APIs REST de alta velocidad (`POST /api/v1/oauth/token` y `POST /api/v1/access/evaluation` en `../microservicios/motor-pdp`; `GET /internal/v1/identities/*` en `../microservicios/pip-identity-service`) desplegadas en GKE Autopilot detrás de Internal Load Balancer privado sobre la Shared VPC, evaluando reglas RBAC + ABAC con caché L2 en Memorystore Redis (`TTL <= 300 s`) y persistencia en AlloyDB for PostgreSQL 16 (`RNF-REN-01..06`, `D-06`).
- **API de Administración (`api-pap`) y Consola Web (`frontend` SPA)**: Gestión centralizada y delegada con 3 roles de consola (**Superadministrador de Seguridad Informática**, **Administrador de Aplicativo** y **Auditor** de solo lectura) de activos tecnológicos, clientes OIDC/M2M, catálogo de rutas, tipos de usuario, roles, permisos atómicos, perfiles, grupos lógicos y asignaciones territoriales/organizacionales, protegida detrás de Cloud IAP.
- **Sincronizador de Identidades (`sso-sincronizador`, Solo Lectura) y Conciliación (`sso-conciliacion-job`)**: Cloud Run Service (`../microservicios/sincronizador`) y Cloud Run Job (`../microservicios/conciliacion-job`) con Direct VPC Egress hacia la Shared VPC, gobernados por Cloud Pub/Sub, Cloud Tasks y Cloud Scheduler para sincronizar hacia AlloyDB los eventos de Google Cloud Identity / Workspace sin escribir nunca en Google Workspace (`<= 28 req/s`, `R-02`).
- **Publicador de Aplicaciones (`sso-publicador-job`)**: Cloud Run Job aislado (`sa-sso-publicador`) que genera en tiempo de ejecución blueprints del catálogo de aplicaciones clientes y ejecuta despliegues en Google Cloud Infrastructure Manager con bloqueo consultivo en AlloyDB (`pg_try_advisory_lock`).
- **Especificación y Paquete Estándar SP/RP (C2.2)**: Contratos OpenAPI 3.1, perfiles OIDC/SAML, suite de pruebas de conformidad y guía de integración.
- **Fuera de alcance**: La modificación e integración de las dos aplicaciones legadas (**Subcomponente C2.3**) no forma parte de este desarrollo.

## Stack de este repositorio

Valores ratificados en `.specify/memory/constitution.md` (sección **Stack de este proyecto**, 100% determinista sin variantes ambiguas):

- **Lenguaje y Diseño**: TypeScript 5.8+ (`strict: true`) sobre Node.js 22 LTS en repositorios independientes (`../microservicios/*`; imagen base `node:22-alpine`); Terraform `1.5.7` (HCL puro en el repositorio separado `../iac-terraform`). Arquitectura Hexagonal + principios **SOLID** + **DRY** en el paquete transversal `@minedec/shared` (`../microservicios/shared/`, publicado en GitLab NPM Package Registry) + **Inyección de Dependencias con `InversifyJS` (`inversify`) configurado exclusivamente en el Composition Root (`container.ts` / `ContainerModule`)**, manteniendo `domain/` y `application/` 100% libres de decoradores (`@injectable()` / `@inject()`) mediante decoración dinámica externa (`decorate(injectable(), ...)`) o `toDynamicValue()`.
- **Dependencias**: Backend con **Express 5** (100% único framework HTTP), `oidc-provider` (certificado por la OpenID Foundation, para `sso-oidc`), `inversify`, `zod` (100% único validador runtime), `jose` (JWT/JWKS RS256), `pg` + `pg-format` (AlloyDB), `ioredis` (Redis), `helmet`, `@google-cloud/*` / `googleapis`, `pino`. Frontend con React 18 + Vite + TypeScript + Tailwind CSS / shadcn/ui.
- **Datos**: AlloyDB for PostgreSQL 16 (PIP primario + clientes OIDC `client_id`/`redirect_uris` + `auditoria_evento` append-only con hash SHA-256), Memorystore for Redis (caché L2 con TTL 300 s, sesión central y códigos efímeros de `sso-oidc` conforme a `DA-11`), Cloud Storage (blueprints, estado Terraform gestionado por Infrastructure Manager y archivo forense WORM con `retention_policy` bloqueada), Cloud Logging y BigQuery (auditoría analítica append-only con IAM segregado y `deletion_protection = true`).
- **Tests y Calidad**: **Jest + Supertest** (100% único runner unitario e integración, cobertura ≥ 70%), **Playwright** (100% único runner E2E de Consola SPA), **ESLint + Prettier**, y suite de 8 pruebas de conformidad SSO (incluyendo prueba de aceptación del SLA de revocación `<= 300 s`).
- **Plataforma, Red Compartida (Shared VPC) y Segmentación Oficial (`/20`, `/23`, `/24`)**: GCP — Proyectos de servicio SSO (`mec-003-sso-des`, `mec-003-sso-pre`, `mec-003-sso-pro`) conectados a la Shared VPC de los proyectos host (`mec-003-sha-net-des`, `mec-003-sha-net-pre`, `mec-003-sha-net-pro-511014`; con soporte de VPC local en `mec-003-sso-des` durante pruebas de desarrollo), utilizando exclusivamente los **3 segmentos de máscara oficiales (`/20`, `/23`, `/24`)**: `/24` para la subred primaria `snet-sso-ue1` (nodos GKE + Cloud Run Direct VPC Egress), `/23` dividido en dos `/24` contiguos para Private Services Access (`psa-sso-sql-<ambiente>` exclusivo para AlloyDB/Cloud SQL y `psa-sso-<ambiente>` para Memorystore Redis), y `/20` dividido en dos `/21` contiguos para los rangos secundarios de GKE (`pods` y `services`, con plano de control GKE vía PSC `master_ipv4_cidr_block = null`). GKE Autopilot (**5 servicios**: `sso-oidc`, `motor-pdp`, `api-pap`, `frontend` y `pip-identity-service`), Cloud Run Service/Jobs (`sso-sincronizador`, `sso-conciliacion-job` y `sso-publicador-job`), Google Cloud Infrastructure Manager (Terraform `1.5.7` invocado con `sa-infra-manager` desde `.gitlab-ci.yml` usando `gitlab-runner@gitlab-servinformacion.iam.gserviceaccount.com`), Cloud Load Balancing + Cloud Armor + IAP, y PEP en Apigee X (Alt. 1) o GKE Gateway API / Envoy (Alt. 2).
- **Tipo**: Plataforma central de autorización y gestión de accesos SSO (Subcomponente C2.2) en arquitectura multirrepositorio en GitLab (`git.sitimapa.co`).
- **Issuer (`iss`)**: Doble nivel conforme a `D-01` y `DA-11`: `https://accounts.google.com` como único IdP primario validado por `sso-oidc` mediante su único cliente OAuth 2.0 en Google Cloud; `https://login.sso.<dominio>` (`sso-oidc`) como Issuer OIDC ante todas las aplicaciones integradas (emitiendo `id_token` `RS256` con `aud` exclusivo por aplicación); y `motor-pdp` como emisor de tokens `client_credentials` (`/api/v1/oauth/token`) y de `X-Minedec-Assertion`.

## Identidad y Federación (Conecta MINEDEC C2.2)

- **IdP Único Primario (`D-01` / `RF-GI-01`) e Intermediario OIDC (`sso-oidc`, `DA-11`)**: Google Cloud Identity / Google Workspace es el único IdP primario para validar las cuentas institucionales (`D-01`, prohibido integrar Active Directory o LDAP en el SSO web), teniendo a `sso-oidc` como su **único cliente OAuth 2.0 registrado en Google Cloud** (`DA-11`). Todas las aplicaciones (Patrón 1 Nativo y el PEP del Patrón 2 Perimetral) inician sesión OIDC (`Authorization Code + PKCE S256`) contra `sso-oidc` (`https://login.sso.<dominio>`), con `client_id` OIDC y `redirect_uris` por aplicación en AlloyDB.
- **Solo lectura sobre Workspace**: Conecta MINEDEC no crea, modifica ni suspende cuentas en Google Workspace; sincroniza en modo de solo lectura.
- **Alcance exclusivo de Personas Naturales y Clave Natural (`CEDULA`) Inmutable**: Conecta MINEDEC autentica y autoriza **exclusivamente personas naturales** (queda prohibido modelar `RUC` societario o personas jurídicas; cuando una persona natural con régimen `HONORARIOS_PROFESIONALES` / `CONTRATISTA` provenga con RUC de 13 dígitos, se normaliza a sus primeros 10 dígitos como `CEDULA`). En negocio, la persona se identifica por `(tipo_identificacion, numero_identificacion)` (`CEDULA`, `PASAPORTE` o `CODIGO_MINEDEC`), que Conecta MINEDEC resuelve y devuelve en `/api/v1/access/evaluation` y en las cabeceras `X-Minedec-*`. En la tabla física `persona_identidad` (AlloyDB), la clave primaria técnica es `id_interno (UUID v4)` inmutable para proteger las llaves foráneas y la tabla `auditoria_evento` (`append-only`), mientras que **`CEDULA` es una clave natural `UNIQUE` estrictamente inmutable una vez consolidada** (solo se admite la transición unidireccional `CODIGO_MINEDEC -> CEDULA` preservando `codigo_minedec_anterior`).
- **Protocolos**: OIDC Authorization Code + PKCE S256 contra `sso-oidc` (principal, `DA-11`) y SAML 2.0 SP-Initiated (alternativo). Los roles nunca viajan en la aserción de Google ni en el `id_token` de `sso-oidc`; siempre los decide `motor-pdp`.
- **Revocación Verificable, Fail-Close y Cero Telemetría de Latencia en Node.js**: Cualquier baja o revocación purga Redis de forma inmediata vía Pub/Sub (`sso-revocaciones` / `sso-pip-cache-invalidation`, tanto la caché de autorización como la sesión central de `sso-oidc`) y garantiza invalidación en **`<= 300 segundos` como límite duro absoluto** (`RF-GI-06`, `RF-AUT-06`, `PI-07` por TTL en Redis), verificable mediante prueba de aceptación automatizada. Si Conecta MINEDEC falla o no responde, se niega el acceso (`fail-close`). Conforme a `RNF-REN-01..06`, `D-06`, Principio V.4 y Principio XIII, los servicios Node.js **no calculan duraciones por petición (`Date.now() - startedAt`) ni exponen campos de latencia en respuestas HTTP**; toda medición de latencia se delega a la infraestructura (Cloud Run, GKE/Envoy y Cloud Trace).

## Ciberseguridad y DevSecOps (Constitución IV, IX, XIII, XIV, XV, XVI, XVII y XVIII)

- **Zero Secret y Rotación (`<= 90 días`)**: Cero credenciales o llaves privadas en código, `.tfvars` o imágenes. 100% en Google Secret Manager (AES-256) con rotación periódica `<= 90 días` (ventana de gracia dual para secretos OIDC/M2M y llaves JWKS `RS256` de `sso-oidc` y `motor-pdp`), sustitución `< 1 h` ante compromiso y auditoría de accesos. Secretos OIDC (`SSO_OIDC_CLIENT_SECRET`) y `client_credentials` guardados solo como hash SHA-256 en AlloyDB.
- **Identidad GCP sin llaves (Nomenclatura `sso-*`)**: Cuentas de servicio dedicadas de mínimo privilegio (`sa-sso-core`, `sa-sso-sync`, `sa-sso-sync-job`, `sa-sso-publicador`, `sa-infra-manager`, `sa-workspace-reader` y `gitlab-runner@gitlab-servinformacion.iam.gserviceaccount.com`) con Workload Identity en GKE, metadata server en GitLab Runner / Cloud Run y `signJwt` de corta duración para delegación de dominio. Prohibido usar llaves JSON.
- **Codificación segura**: Validación estricta de esquemas (`zod`), **valores de datos SQL 100% parametrizados (`$1, $2`)**, **identificadores SQL dinámicos exclusivamente por lista blanca cerrada (`allowlist` + regex `safe_sql_identifier` + escape `%I` con `pg-format`)**, migraciones DDL estáticas versionadas en Git, normalización de rutas rechazando rutas ambiguas (`%2F`, `..`), prohibición de `dangerouslySetInnerHTML`, prohibición total de `localStorage` y de guardar tokens/roles en `sessionStorage` (permitido solo para estado efímero PKCE `state`/`nonce`/`code_verifier`). Cabeceras HTTP de nivel A (`HSTS`, `CSP`, `X-Frame-Options: DENY`, `X-Content-Type-Options: nosniff`).
- **Auditoría Inmutable de 3 Capas**: Archivo forense WORM en Cloud Storage con `retention_policy` bloqueada (`is_locked = true`), BigQuery en modo `append-only` con IAM segregado y `deletion_protection = true`, y tabla `auditoria_evento` en AlloyDB con privilegios solo `INSERT/SELECT` y encadenamiento SHA-256.
- **Contenedores, GitLab CI/CD y Peer Review**: Imágenes Docker `non-root` (`USER node`/`appuser` sobre `node:22-alpine`), separación de backend y estáticos, exclusión de compilados (`dist/`, `node_modules/`, `.terraform/`) en `.gitignore`, ramas `spec/00X-...` sincronizadas entre repositorios en GitLab (`git.sitimapa.co`), revisión de código por pares obligatoria en Merge Request (MR) con checklist OWASP y aprobación `CODEOWNERS` en rutas críticas, más escaneos SAST (`ESLint`), SCA (`npm audit`) y detección de secretos (`Gitleaks`) en `.gitlab-ci.yml`.

## Cómo generar especificaciones

Camino oficial: `specify` → `clarify` → `plan` → `checklist` → `tasks` → `analyze` → `implement` → `converge`.

Antes de `/speckit-specify`, `/speckit-plan`, `/speckit-tasks` o `/speckit-implement`:

1. Leer el índice canónico OKF: `knowledge/index.md` y seguir los enlaces hacia los conceptos relevantes.
2. Citar los conceptos OKF usados en `Referencias OKF / knowledge` y `Assumptions`.
3. **Verificación obligatoria contra Google Developer Knowledge (`retrieving-developer-knowledge`)**: Queda **estrictamente prohibido** que Spec Kit genere arquitectura, decisiones técnicas (`research.md` / `plan.md`), tareas (`tasks.md`), contratos de integración, permisos/roles IAM, comandos `gcloud`, llamadas a SDKs `@google-cloud/*` / `googleapis` o recursos Terraform (`google` / `google-beta`) basados en memoria de preentrenamiento sin antes consultar la documentación oficial vigente mediante la skill `.agents/skills/retrieving-developer-knowledge/SKILL.md` (servidor MCP `google-developer-knowledge` / API `https://developerknowledge.googleapis.com/mcp` con proyecto de cuota `mec-001-dev-aurora`). Todo `research.md` y `plan.md` debe citar explícitamente los nombres de recursos documentales autoritativos (`documents/...`) consultados en Google Developer Knowledge.
4. En la spec: conservar `User Story`, `FR-001`, `SC-001`. **No** declarar lenguaje, stack ni recetas OWASP.
5. En el plan: rellenar Technical Context con el stack de esta constitución. Cuerpo íntegramente en **español**.
6. Si falta un hecho de negocio o depende de una decisión pendiente (`D-02` a `D-21`), marcar `[NEEDS CLARIFICATION]`. **No inventar** reglas ni topología GCP.

Vocabulario institucional: AMIE, cantón, zona, distrito, circuito, establecimiento, docente, administrativo, estudiante, ciudadano, representante, viceministerio, cédula.

## Quality gates

- Revisión por pares (MR en GitLab) con checklist OWASP y aprobación `CODEOWNERS` en rutas críticas.
- Cobertura ≥ 70% en pruebas unitarias e integración (`Jest + Supertest`).
- Pruebas E2E de flujos críticos en la Consola SPA (`Playwright`) y prueba automatizada de revocación `<= 300 s`.
- Especificación OpenAPI 3.1 actualizada en cada cambio de contrato.
- Verificación documental oficial de Google Cloud / Workspace mediante `retrieving-developer-knowledge` (`documents/...` citados en `research.md`).
- Prohibido desplegar a GCP saltándose GitLab CI (`.gitlab-ci.yml`) / Google Cloud Infrastructure Manager (`sa-infra-manager`).
